# eval/ — upgrade-analyzer ゴールデン評価セット

プロンプト（`upgrade-analyzer.md`）を改修するたびに、**BC抽出の精度が上がったか下がったかを数値で検証する**ための回帰評価基盤。
「改善したつもりが recall が下がっていた」を防ぐ。v4.5 で導入。

## 構成

```
eval/
├── README.md          # このファイル
├── score.py           # スコアリングスクリプト（標準ライブラリのみ）
└── cases/
    └── next_14.0.0_to_15.3.2.json   # 正解BCリスト（公式ガイドから人手キュレーション）
```

## 使い方

```bash
# 1. 評価対象のアップグレード分析を実行（ケースと同じパッケージ・バージョン）
#    Claude Code で: /upgrade-analyzer next 14.0.0 15.3.2

# 2. 生成されたMDレポートをスコアリング
python3 eval/score.py reports/next_14.0.0_to_15.3.2_*.md \
  --case eval/cases/next_14.0.0_to_15.3.2.json

# CI等で閾値を割ったら失敗させる場合
python3 eval/score.py <report.md> --case <case.json> --min-recall 0.9
```

## 指標の定義

| 指標 | 定義 | 測定方法 | 目標 |
|------|------|---------|------|
| **recall** | 正解BC（must_find）のうちレポートに記載された割合 | score.py が自動算出（正規表現マッチ） | ≥ 90% |
| **precision** | レポート記載BCのうち実在するものの割合 | **人手確認**: 各BCの「根拠引用」が出典URLの原文と一致するか照合 | 100%（引用義務化により構造的に担保） |
| **判定一致率** | 同一入力での複数回実行で総合リスク・推奨度が一致する割合 | 同一コマンドを2〜3回実行してJSONサマリーの `risk` / `recommendation` を比較 | 100%（2-5ルーブリック準拠） |

## プロンプト改修時の運用

1. 改修**前**に評価を1回実行し、recall を記録する（ベースライン）
2. 改修**後**に同じケースで再実行し、recall の変化を確認する
3. recall が下がった場合は改修をリリースしない（原因を特定して修正）
4. 結果はコミットメッセージまたは Todo.md に「v4.5: recall 82%→100% (11/11)」の形式で記録する

## ケースの追加方法

1. 公式アップグレードガイド・リリースノートが充実しているアップグレードを選ぶ
2. **一次情報のみ**から正解BCを人手でキュレーションし、`cases/{pkg}_{from}_to_{to}.json` を作成
   - `patterns`: レポートMD本文に対する正規表現（大文字小文字無視・いずれか1つ一致で検出扱い）
   - パターンは過剰マッチ（BCに触れていないのに一致）しないよう具体的に書く
3. `curated_at` と `sources` を必ず記録する（正解自体の監査可能性のため）

### 推奨追加ケース（未整備）

- `django 4.2.0 → 5.1.0`（PyPI・設定系BCが多い）
- `spring-boot 3.1.0 → 3.3.0`（Maven・プロパティ名変更が多い）
- パッチ版で挙動変更があった事例（semver過信の検出用）

## 注意事項

- score.py の正規表現マッチは「レポートのどこかに記載があるか」の判定であり、記載位置（BCセクションか参考情報か）までは見ない。recall 100% でも最終レポートの品質確認は必要
- 正解ケースはキュレーション時点の公式情報に基づく。Toバージョンより後に公式ガイドが更新された場合はケースの見直しを行う
